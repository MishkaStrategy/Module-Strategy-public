# Platform release and rollback procedure v2

**Scope:** issue #387, GAP-009. This procedure covers a candidate for the operational **PAPER/research** product only. It does not authorize live trading, private exchange credentials, deployment, publishing, merge to `main`, or creation of a stable tag/release. A stable release is a separate accountable-owner decision.

## 1. Readiness rule

Treat a candidate as **not releasable** until every applicable gate below has candidate-bound, reviewable evidence and the independent release verifier and accountable owner accept that exact candidate. A structurally valid manifest is not acceptance. The current `scripts/platform_release_manifest.py` deliberately refuses an `accepted` decision because it has no external trusted inventory baseline or authenticated evidence and owner-approval attestation. Validation must run from a protected, independently pinned identity; candidate-controlled code or manifest data cannot authenticate its own evidence.

At the time this procedure was written, there is no populated v2 release manifest, trusted release evidence, accepted decision, or demonstrated clean Python 3.12/3.13 installation. The procedure therefore describes future gates as well as the structural checks already implemented; it records no release approval.

The console's Node/npm build, deterministic package, Linux serving runtime and Darwin browser acceptance are not yet represented in v2's canonical material identity. [Web Console Release Contract v1](WEB_CONSOLE_RELEASE_CONTRACT_V1.md) is a pending adjunct draft only. It does not resolve a v2 `unknown-blocking` Console scope or independently confer acceptance. A future versioned envelope and protected combined verifier must require the sidecar-equivalent fields alongside every existing v2 obligation before Console acceptance is possible.

## 2. Candidate freeze and identity

1. The owner selects a proposed source commit and support profile for the intended PAPER/research use. Record the canonical repository, exact 40-character source commit, candidate identity, profile identity, and intended target environment in the v2 manifest. The current validator requires the source checkout to be clean and at that exact commit and resolves referenced files from the tracked source at that commit and from the candidate bundle.
2. Freeze the candidate inputs: source tree, component inventory, package artifacts, lock files, compatibility contracts, migration implementations, rollback procedures, composition, and support profile. Record hashes and identities as required by the schema. Do not treat a branch name, moving tag, local working tree, or mutable artifact URL as an immutable candidate identity.
3. Keep candidate, profile, and manifest-envelope identities separate. A change to candidate inputs (source, components, artifacts, locks, compatibility contracts, migrations, rollback procedures, or composition) requires recalculating `candidate_id` and invalidates candidate-bound evidence. A support-profile change (including deployment targets, `acceptance_requirements`, or inventory) requires recalculating `profile_id` and invalidates profile-bound evidence. Adding or replacing evidence rows or lock-reconstruction receipts changes the manifest-envelope digest, not `candidate_id` or `profile_id`; those rows remain bound to the corresponding candidate/profile IDs. Replacing or removing an evidence digest invalidates any decision that references it. Unrelated passing evidence may be retained only while it remains bound to unchanged inputs and is independently verified. Rerun affected gates, then repeat the full acceptance verification against the updated envelope; never rely on an unchanged display version or release label as proof that identities remain valid.

The implemented validator checks schema shape, identities and digests, clean exact source, tracked file references, source-pinned inventory relationships, package metadata and internal dependency compatibility, Python lock pins and reconstruction receipts, and evidence-to-candidate/profile/source/artifact/gate/environment bindings. Generic acceptance evidence must match its declared `(gate, component_id, environment)` requirement; lock reconstruction and build records remain bound to deployment targets. For each declared Python distribution it reads wheel and modern single-root `.tar.gz` sdist metadata without extraction or execution, bounds archive size (256 MiB compressed, 1 GiB expanded, 100,000 entries, 8 MiB per metadata file), and checks filename/archive/metadata identity against the source-pinned component. Core metadata must use supported major version 2, with `Metadata-Version` at least 1.1 in wheels and 2.2 in modern sdists. It rejects ZIP64 and multi-disk wheels before constructing `ZipFile`, so central-directory member disk-start and local-header offsets are checked and the entry limit is enforced before entry objects are allocated. For sdists, `project.version` may be statically declared or declared dynamic; in the latter case the generated `PKG-INFO` version must match the sdist filename/root and source-pinned component. The accepted `project.dynamic` fields are restricted to the validator's explicit PEP 621 allowlist; conflicting or malformed static/dynamic version declarations are rejected. An accepted candidate must include at least one valid wheel and one valid sdist for every Python component. These are structural and consistency checks; they do not prove provenance, authenticity, safe installation, source correspondence, reproducibility, that a test was actually run correctly, or that evidence is trustworthy.

## 3. Build and compatibility gates

1. Produce the candidate package artifacts from the frozen source and retain their exact digests. Verify that the artifacts correspond to the declared components and package metadata.
2. For the declared target environment, build and runtime locks must be complete and hash-pinned. For Python, the current v2 contract requires exact stable CPython 3.12 and 3.13 runtime identities, separate build/runtime locks for each, and a reconstruction receipt for each lock/runtime/environment tuple. Receipts bind the candidate, source, lock digest, observed runtime, run/attempt, outcome, and normalized resolved distribution inventory. The validator cross-checks lock pins against those receipts and candidate component versions.
3. Run clean, isolated builds and installations on each supported runtime, then exercise the documented package imports, application startup, and declared PAPER workflows. Capture sanitized, candidate-bound evidence for each required gate. The current validator checks declared metadata, dependency ranges, lock contents, and receipt consistency; it does **not** perform a clean install, establish network/package-index provenance, or certify runtime behavior. Those remain release gates requiring independent execution and evidence.
4. Validate compatibility contracts against the exact previous and candidate versions named in the manifest. Exercise upgrade and downgrade/restore behavior only using the candidate-specific migration and rollback procedure below. Do not infer compatibility from matching version strings alone.

## 4. Migration, backup, and rollback contract

Before any state-changing operation is considered, the candidate must declare each applicable migration (`from`, `to`, kind, implementation reference) and each rollback (`from_candidate`, `to_candidate`, procedure reference). For acceptance, the schema requires at least one migration and rollback entry; the validator requires evidence for every migration and rollback, and accepted coverage includes those gates. A schema reference is not proof that the procedure works.

The release owner and operator must review a candidate-specific, tested procedure that identifies the state being changed, preconditions, backup contents and location, integrity/restore check, migration order, success criteria, stop points, rollback trigger, restoration steps, and post-restore verification. Take and verify backups before a migration only as that tested procedure specifies. Use rollback only if its tested evidence demonstrates restoration for this exact source, data/state format, and candidate transition. Never assume a database downgrade is safe or that reinstalling old code reverses a data migration.

If an applicable backup/restore or migration/rollback path lacks a tested candidate-bound procedure or evidence, **do not start the state change**. Stop, preserve the candidate and sanitized diagnostic evidence, and return the candidate to the owner for remediation and fresh validation. If execution fails or diverges from the tested procedure, stop at the documented checkpoint; do not improvise a repair or destructive rollback. Follow only the pre-reviewed recovery procedure, or escalate to the accountable owner/operator while preserving recoverable state.

## 5. Evidence and independent acceptance

Evidence records must bind to the candidate ID, profile ID, exact source commit, component and artifact digest, gate, the environment declared for that `(gate, component_id)` in `acceptance_requirements`, run ID, attempt, outcome, and evidence digest. Lock reconstruction and build evidence bind to their deployment target environments. Keep raw material in the approved restricted evidence store; publish only sanitized outputs, with credentials, private exchange details, personal data, and unrelated host data removed. Sanitization must not remove the information needed to verify the recorded result. Preserve a traceable mapping from each evidence digest to its source record.

Before acceptance, an independent verifier must check evidence authenticity and provenance, required gate coverage, exact candidate and profile identities, package/dependency compatibility, migration/rollback evidence, and the external trusted inventory baseline. The accountable owner then reviews the verified evidence and records an authenticated decision for the same candidate and profile. Pending, failed, blocked, canceled, missing, mismatched, or unauthenticated evidence is not a pass. Re-run affected gates after any candidate change.

## 6. Release decision and stop conditions

The accountable owner makes the PAPER/research release decision only after the independent verifier reports complete passing coverage and the operator confirms the documented recovery prerequisites. A separate explicit owner decision is required for a stable tag or public release; acceptance of a candidate does not create that authorization.

Abort or hold the release if any of the following applies:

- the exact source commit or bundle is dirty, has changed, or does not match the manifest;
- schema, identity, digest, package metadata, dependency, lock, reconstruction, or compatibility validation fails;
- any supported-runtime clean build/install or required PAPER/research gate is absent, fails, or has untrusted evidence;
- migration, backup/restore, or rollback procedure/evidence is missing, stale, or not demonstrated for this candidate transition;
- inventory roles remain unresolved, required capability/gate coverage is incomplete, or evidence is pending, blocked, canceled, failed, or mismatched;
- the independent verifier or accountable owner has not accepted the exact candidate/profile pair;
- the proposed action requires live trading, private exchange credentials, deployment, or another activity outside this PAPER/research authorization.

On abort, do not advance the candidate, perform a state-changing migration, or represent it as released. Preserve the frozen candidate and sanitized failure evidence, identify the failed gate, and return the issue to the owner for a scoped correction and revalidation.

## 7. Boundaries and implementation status

This procedure is documentation for the #387 release contract. The current v2 schema and validator provide structural validation and fail-closed acceptance behavior, but no actual manifest or trusted evidence is present. Clean Python 3.12/3.13 installation, independently authenticated execution/evidence, operational backup/restore, verified migration and rollback, release acceptance, stable tagging, and deployment are future work requiring their own evidence and authorization. All activities described here remain within PAPER/research; live trading and use of private exchange credentials are explicitly excluded.
