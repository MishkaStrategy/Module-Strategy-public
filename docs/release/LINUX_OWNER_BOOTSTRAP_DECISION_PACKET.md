# Linux owner bootstrap decision packet

**Purpose:** obtain the owner decisions needed before implementing a Linux Stage-1 owner adapter. This packet records source facts, a proposed contract for review, and decisions that remain unselected. It does not authorize service activation, Linux support, or PAPER/release acceptance.

## Source facts

- The current owner-manager contract is Darwin-specific. `ReconstructedStage1Owners` contains a strategy package, a `ResearchRunner`, its prepared experiment, and a recovered Trading Runner owner. `Stage1OwnersLoader` returns that bundle; `Stage1SourcesFactory` receives the bundle's strategy/research/trading interfaces and returns `Stage1DeploymentSources` ([manager types](../../scripts/system_acceptance_stage1_service_manager.py#L42), [manager factory protocol](../../scripts/system_acceptance_stage1_service_manager.py#L50)). The surrounding config is explicitly a launchd-owned process and fixes loopback ports 8780, 8781, and 8782 ([manager config](../../scripts/system_acceptance_stage1_service_manager.py#L64)). These are current Darwin implementation facts, not Linux owner or host selections.
- `Stage1DeploymentSources` is the typed input boundary for materializing production composition. It requires `full_rc_sha`, dataset ID/version/timeframe/storage root, strategy package, Backtest A/B and recovery configs, performance config, Research Runner and prepared research, Trading Runner/query, and environment/final verification callbacks. Funding source, valuation policy, mark-price source and resource sampling are optional fields ([source fields](../../scripts/system_acceptance_stage1_deployment.py#L99)). Materialization expects research to be prepared already, resolves owner identities, and does not create a Trading Runtime ([materializer contract](../../scripts/system_acceptance_stage1_deployment.py#L174)).
- `Stage1Lifecycle` remains platform-neutral: it accepts registered start/close callbacks and acquired resources, but does not load owners, interpret paths, choose commands, or grant authority. The manager now creates one lifecycle before bootstrap and exposes an explicit managed loader/source-factory pair that receives it; each factory can register an acquired resource immediately with `lifecycle.acquire`. The legacy no-argument loader/four-argument source-factory pair remains available as a mutually exclusive compatibility path and cannot register bootstrap resources ([managed protocols and selection](../../scripts/system_acceptance_stage1_service_manager.py#L40), [manager startup boundary](../../scripts/system_acceptance_stage1_service_manager.py#L127), [lifecycle acquisition](../../scripts/system_acceptance_stage1_lifecycle.py#L25)).
- Loader, validation, source building, materialization, proof writing, and service start now share the same rollback boundary. Cleanup runs in reverse acquisition order, attempts all registered closers, and preserves primary and cleanup failures together. Concurrent starts are serialized; `close()` marks shutdown and waits for an in-flight start to finish or roll back before returning. A constructor that raises before it returns a resource must clean up its partial construction itself, because the lifecycle cannot register an object it did not receive ([acquire contract](../../scripts/system_acceptance_stage1_lifecycle.py#L25)).
- Systemd support currently consists of a caller-configured unit renderer/installer. Its module says it neither activates the unit nor claims support for a Linux image; owner-selected image and clean-host acceptance remain required ([systemd scope](../../scripts/system_acceptance_stage1_systemd.py#L1)). The release support-profile decision records Linux/VDS as the target topology while leaving distribution, architecture, ABI, service manager and host constraints open ([profile status](PAPER_SUPPORT_PROFILE_DECISION.md#L21)); it also lists exact Linux host choices as owner decisions ([profile decisions](PAPER_SUPPORT_PROFILE_DECISION.md#L53)).
- The existing restart handoff describes the intended deployment-owned boundary: an executable wrapper constructs fixed typed loaders, component/source factories, private tokens and config; the repository does not invent missing owner identities/adapters ([handoff contract](../../docs/system_acceptance/STAGE1_MAC_RESTART_HANDOFF_V1.md#L64)).

### Gate/environment scope reconciliation

The repository records one Linux/VDS PAPER deployment target and separate Darwin acceptance; schema v2 keeps exactly one `target_environments` entry while mapping acceptance scopes by gate, component and environment ([selected topology](PAPER_SUPPORT_PROFILE_DECISION.md#L7), [profile decision](PAPER_SUPPORT_PROFILE_DECISION.md#L13), [schema fields](../../schemas/platform-release-manifest-v2.schema.json#L822)). The inventory assigns `operations:mac-service-reconnect` to `real_host` and #873 ([inventory row](../../profiles/component-inventory.json#L143)); the planner explicitly requires that gate's profile scope and workload/output environment to be `acceptance_darwin` ([planner gate rule](../../scripts/fixed_workload_planner.py#L420), [workload rule](../../scripts/fixed_workload_planner.py#L520)). This can remain Darwin acceptance.

The inventory names the required two-hour gate only as `soak:paper-two-hour` and links #866 ([inventory row](../../profiles/component-inventory.json#L288)); the release checklist likewise says the soak must pass on the exact supported host/candidate ([checklist](../../RELEASE_CHECKLIST.md#L47)). The live [issue #866](https://github.com/MishkaStrategy/Module-Strategy/issues/866) explicitly requires an Apple Silicon Mac. The planner has no fixed-host rule for this generic soak gate: profile acceptance scopes and workload environment select its environment, while the Darwin-specific rule is limited to `operations:mac-service-reconnect` ([planner Darwin-only gate set](../../scripts/fixed_workload_planner.py#L28), [scope validation](../../scripts/fixed_workload_planner.py#L403)). Therefore, under Linux/VDS deployment plus Darwin acceptance, gate mapping alone does not establish whether the Mac-only #866 soak is sufficient evidence for Linux release.

The owner must choose one scope: preserve #866 as the Mac soak and add explicit Linux two-hour deployment acceptance, or re-scope #866 to Linux and decide whether a Darwin two-hour soak remains required. A conservative engineering proposal is to preserve the Mac soak and add Linux acceptance while retaining Darwin reconnect acceptance; that proposal is not approved. Likewise, the live [issue #933](https://github.com/MishkaStrategy/Module-Strategy/issues/933) describes Mac provisioning composition, while the inventory records the generic `composition:paper-owner-provisioning` gate ([inventory row](../../profiles/component-inventory.json#L111)); Mac provisioning does not establish a Linux provisioner. These distinctions fit the existing target/acceptance separation; they do not imply a schema redesign or authorize acceptance.

## Engineering proposal for owner review

Approve a fixed Linux bootstrap contract before adapter implementation:

1. Define a typed, deployment-owned Linux owner/source factory with explicit inputs and outputs. Its output must provide the same semantic owner graph currently represented by `ReconstructedStage1Owners`, plus exactly one `Stage1DeploymentSources` value assembled from the required source fields above. The factory must bind each field to an identified authoritative owner or approved configuration source; it must not infer identity from caller input, arbitrary paths, environment variables, or placeholder values.
2. Define Linux owner/resource ownership at acquisition time. Managed factories must register every successfully constructed resource immediately with the supplied lifecycle. A partially constructed resource must clean itself if its constructor fails before returning; the lifecycle can only own returned objects. No Linux owner graph or resource factory is selected by this reusable contract.
3. Require reverse-order cleanup on startup failure and stop, attempt every cleanup even when one fails, and keep startup and rollback failures observable together. The same cleanup contract must cover termination signals. State paths and private tokens must be passed through typed configuration, excluded from repr/log/proof output, and validated before use; the decision must identify the owner of permissions, persistence, backup and recovery policy.
4. Keep host selection separate from lifecycle mechanics. The Linux adapter may reuse the platform-neutral lifecycle core, but the owner must select the Linux image, architecture/ABI, Python patch builds, systemd baseline, service identity, executable/work directory, state location and permissions, secret delivery, network exposure and recovery policy. Existing Darwin defaults do not resolve those choices.
5. Keep bootstrap and cleanup callbacks synchronous, finite, and non-reentrant with respect to manager `start()`/`close()`. Manager shutdown waits for bootstrap drain without a timeout. Any independent concurrent use of the lower-level lifecycle must coordinate in-flight resource construction before calling `close()`; the lifecycle alone cannot provide that drain guarantee.

This is a proposal for a bounded interface and lifetime contract, not a deployable entrypoint or an implicit selection of any concrete Linux values.

## Owner decisions required

Before implementation, the accountable owner should approve or amend all of the following:

1. **Fixed reconstruction contract:** Which deployment-owned factory constructs the strategy, prepared Research state and already-existing Trading owner? Which exact typed input sources and identity/provenance records does it accept, and which owners are authoritative for each `Stage1DeploymentSources` field?
2. **Factory boundary:** Does Linux expose a loader returning the current four-part reconstructed owner graph, or an owner-approved typed extension? Which source-factory interface receives those owners and creates the exact source bundle? Specify treatment of optional `funding_source`, `mark_price_source`, and `sample_resources`; no omission/default is to be inferred as approved product policy.
3. **Resource lifetime and partial failure:** Which Linux owners/factories acquire each resource, and which typed close action owns it? Managed factories must use immediate lifecycle registration, reverse-order cleanup, attempt-all behavior, and preserve primary errors with cleanup errors. Each constructor owns cleanup of partial state when it fails before returning a resource.
4. **Linux host contract:** Name the distribution/image, architecture, libc/ABI, exact CPython patches, systemd baseline, service user/group, executable and working directory, state path/mount and permissions, token/secret source and rotation owner, network policy, and backup/restore/recovery rules. The current packet intentionally supplies no values.

## Guardrails and next steps

Keep the systemd unit inactive. Do not claim Linux support, Linux host acceptance, trust-root selection, predecessor compatibility, or release acceptance from this contract or the existing renderer. No owner/workload data or protected workload is needed to decide the interface.

After the owner records these decisions, bind the Linux bootstrap/config boundary and fixed factories to the lifecycle contract and add any owner-specific synthetic checks, including state/token-safe proofs. The generic Darwin manager lifecycle contract and synthetic rollback/concurrency tests are implemented in this candidate; they do not provide a Linux adapter. Separately, complete the selected host/toolchain, trust, predecessor, and clean-host acceptance gates before making any Linux support or release claim.
