## Other completeness obligations

- **Component compatibility:** the Results Registry has 17 schema families with a source and packaged copy (34 files). A release contract must bind the semantic compatibility/version relationship, not only enumerate paths.
- **Migrations and recovery:** the base has a legacy download-config conversion that emits a typed request and avoids overwriting its destination, and System Acceptance has store initialization/version checks. These facts do not establish a release upgrade path or rollback. Inventory the supported predecessor and classify initialization, config conversion, database upgrade, backup/restore and rollback separately; do not infer a rollback guarantee from a converter.
- **Evidence coverage:** evidence must be required per supported component/profile and bind exact source, relevant lock and toolchain identities, build outputs and check results. Accepting any non-empty list of same-source workflow records, or a nullable artifact digest, cannot prove the full profile.
- **Reconstruction:** tests must build each supported profile in clean environments from declared locks. For the console, verify the actual build, asset identity and supported UI/backend contract; a Python-only resolution does not qualify it.
- **Workflow invalidation:** changes to package descriptors, source sets, locks, schemas, validator/generator code, migration inputs and runner-preflight policy must trigger the relevant validator. Workflow YAML alone cannot remove the external trust-boundary requirement for exact-head checks.

## Contract architecture and decision boundary

Use **typed per-ecosystem lock records** as the schema primitive. A generated aggregate index can package those records, but hashing an opaque index is not dependency validation. Each record needs ecosystem and lock format, resolver/package-manager identity, purpose (`build`, `runtime` or `test`), covered components, target environment, immutable lock bytes and digest. Model Python build backends separately from installed runtime dependencies; pin Node/npm as build tools unless an accepted deployment profile requires Node at runtime. Preserve library package ranges and pin the selected release composition in its profile-level resolution identity.

Keep identities acyclic and independently reviewable: a canonical **candidate ID** binds source, package/build artifacts, locks, compatibility declarations, migration/rollback implementations and composition/configuration; a **profile ID** binds the supported topology, required capability matrix and acceptance policy; each evidence subject binds both IDs plus exact source/artifact digests, gate/scenario, sanitized environment, producer/run/attempt, outcome and evidence digest. A final release envelope references the candidate, profile, accepted evidence and owner approval. Adding evidence must not mutate the candidate identity.

The operational profile must be closed over the full required PAPER scope: the 26 Python distributions; Market Data Web Console; operator UI/control scope (#370, with implementation PR #371 merged) and recovery UI (#778); owner-native composition (#933), topology (#400), real-host proof (#873), lifecycle, drift and Risk Supervisor; portfolio coordination (#396); migrations and restore; security; runbooks; and candidate-bound recovery, A/B, and soak gates. Missing or unfinished capabilities must keep the profile unaccepted; the read-only Market Data view cannot discharge PAPER control or recovery workflow requirements.

Owner decisions still needed before a profile can be accepted: supported host/runtime matrix, concrete operator and recovery surfaces, topology, acceptance thresholds, migration reversibility policy, and publication/attestation authority. Schema layout, canonical encoding and validator decomposition are implementation details and can be developed without inventing those values.

Migrate #428's unmerged v1 files into an explicitly versioned replacement before merge. Retain safe-path, exact-source and canonicalization protections; replace the single opaque lock, Python-only environment list and nullable accepted-evidence hashes. Existing v1 fixtures can remain historical structural examples, but cannot count as a full operational candidate.
